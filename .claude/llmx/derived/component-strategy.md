## 1. What is borrowed from Compose, and what v4 already had

Compose's one durable idea is that **what the machine is told exists and what the runtime will accept are the same fact, produced from the same source.** One Zod definition per component yields the prompt, the schema and the render registry, so none of the three can quietly disagree. Everything else Compose ships — the JSON spec format, the expression language, the patch stream, the hosted bridge — exists because there is no compiler anywhere on its path and its model is not holding a checkout. v4 already does that one idea, harder, on two planes: `policy/tokens.json` produces six artefacts held byte-identical, and `style-words.ts` is one pure function both the gallery and Storybook read rendered classes through.

What v4 has never done it for is **components, addresses, screens and data.** **VERIFIED:** "which components exist" is answered independently six times — `readdirSync` in `stories.test.ts`, `adapter-schema.test.ts`, `gallery.test.tsx`, `tokens.test.ts:1560` and `tests/unit/design-system-classes.test.ts:100`, and `import.meta.glob` in `stories.browser.test.tsx:130` — and "which axis tables exist" twice: derived from module exports in `stories.browser.test.tsx` (finding nine, with one recorded attribute override) and hand-imported five at a time in `gallery.test.tsx`. Beyond those, fourteen per-component suites each hand-import their component and its table. That is this repository's named defect — a fact acquiring a second home, agreement indistinguishable from correctness right up to the moment it ends.

The strategy is three words: **derive, then require.** Derive each fact once, from the thing that already holds it; require every derived value to appear in the rendered output; and where nothing can be derived, make the declaration load-bearing so it cannot be false.

## 2. The mechanisms

Each sits at exactly one tier, and **nothing may be added at a lower tier than it could sit at.**

> **Tier 0 — unwritable.** The wrong thing is a compile error or a lint refusal.
> **Tier 1 — derived and required.** The population is derived from the tree; a floor refuses the empty set; every value must appear in the rendered DOM.
> **Tier 2 — declared with a reason.** An absence is recorded with a sentence, so a hole and a decision are distinguishable.

A DOM check is stronger than a source check — it asks what the browser was handed, not what the author claimed — but **which DOM** is part of the check. The node render (`renderToStaticMarkup`) carries a closed, small attribute set; the browser project carries whatever the adaptee stamps at runtime. Every mechanism below names its project, because a check that migrates between them silently changes subject.

## 3. How a screen is built, from a one-line ask to green

The human's ask is one line: *"the employee list."* Everything below is the agent's.

1. **The screen is chosen and recorded.** The human's call; it lives in `STATE.md`. Until then nothing in mechanisms 5–7 is built (rule 2).
2. **The handler first.** Rule 1: the handler *is* the API. Its response object is exported from the handler module. Red first: the handler test before the handler.
3. **The presentational component's props are written before its markup** — the resource union over that response type, produced by `toResource`. From here the compiler holds the state machine: there is no arm in which the data both exists and does not.
4. **The words.** The agent reads the headers of the components it needs. There is no census artefact to read — the census is a function, and functions are for tests, not for reading. The generated catalog stays deferred until step 8's numbers say the reading is expensive; pretending otherwise would be the strategy's only unbacked claim.
5. **The scenes.** The screen's four states are registered in the screen register, each rendering *the presentational component* with the handler's exported object — never a re-composition out of design primitives, because then what is judged is not what ships. Each frame gets its computed address, and addressable elements inside it get theirs.
6. **The look.** `pnpm --filter @xforge/web dev`, then `pnpm gallery:proof <dir>`, which drives its own Playwright Chromium and writes `gallery-light.png`, `gallery-dark.png`, `gallery-compact.png` and a markdown and JSON report. **Looking leaves an artefact the report cannot invent.** That driver is also the answer to the embedded browser: it is a real Chromium and registers the worker, so a data scene is judgeable there rather than unverifiable.
7. **Green**, with each exit code read directly and never through a pipe: lint, types, unit, browser, and byte-identical regeneration of both generators.
8. **The report.** Outcome first; VERIFIED and ASSUMED separated; **the addresses touched and the axis values changed**, named, not described; the scene ids looked at with the proof directory that holds their images; the commands and what they returned; the risk and its signal; and **the components the screen used against the headers read, with line counts** — which is the measurement §7's two DEFERs are gated on, and the only way they can ever be lifted.

If a screen cannot be built this way, outcome four applies: it is declared hand-written with a reason, and it stays ordinary code.

## 4. What this refuses to build, and why

- **A spec format, and its authoring conveniences** — any JSON description of a screen, plus the builders and inference helpers a format needs. TSX plus the compiler is strictly more expressive and strictly better checked, and a spec separates the artefact looked at from the artefact shipped. Compose needs one because its model is remote and its output must render before it is complete; here the model has a checkout and git.
- **An expression language, a visibility predicate language, an action catalog, a validation DSL, a state-store adapter.** Each is a JSON stand-in for something the language already has, needed only because a spec cannot carry a function.
- **A runtime renderer and a registry keyed by name.** The component module is both the contract and the renderer, so there is no join by name and nothing to drift. Compose can only *warn* about that gap; refusing the join removes it.
- **Patch streaming and a stream compiler.** Nothing here renders a document that is still arriving. `git diff` is the patch transport; the dev server is the progressive render.
- **An MCP server, a hosted bridge, a shared session document, presence, a capability URL.** The agent reads the checkout and drives a local browser. The bridge would send design content to a third-party host for a loop that already works locally.
- **A generated component catalog, prompt, or `COMPONENTS.md` — for now.** Every consumer can import TypeScript, so a generated page is a second home plus a second byte-identical burden. It returns when step 8's numbers record a real cost: which components a screen needed against which headers were read.
- **A component manifest emitted by the token generator.** That generator has one subject. A generator with two subjects is two authorities in one file — which is exactly why mechanism 5's allowlist gets its own script and its own diff line rather than a ride on this one.
- **Autofix, repair passes, and any severity below red.** A repaired artefact has passed a check it failed. Compose is fail-open at three layers. So is a Grit plugin whose predicate errors — measured here at `info`, exit 0 — which is why mechanism 5 carries a liveness fixture rather than a promise.
- **A second theme dial.** The token source, with theme rebinding only colour, density only dimension, and contrast asserted before any artefact is written, is the stronger checked form.
- **Components nothing asked for**, a table, a form library before a screen has a form. Rule 2.
- **Aggregating the loop into one script, or any CI, pull-request gate or branch protection.** Removed by the owner on purpose. The fast loop with exit codes read directly is the gate.

## 7. Every Compose mechanism: adopt, adapt, reject

| Compose mechanism | Verdict | Its v4 form, or why not |
|---|---|---|
| One declared vocabulary, everything derived from it | **ADOPT** | The whole strategy. Applied as a derivation function over loaded modules, not a generated file — the modules already are the vocabulary. |
| `defineComponent` / a `.catalog.ts` beside each component | **REJECT** | A second copy of the props joined to the implementation by co-location, checked by nothing. The module is the definition. |
| `defineComponent`'s `slots` and `events` | **REJECT** | Children are ordinary JSX and handlers are ordinary props, both compiler-checked. v4's `data-slot` is a per-element identity marker from the Base UI styling contract and an unrelated idea — which is why mechanism 2's constant is `SLOT_NAMES`. |

| `autoFixSpec` and any repair pass | **REJECT** | A repaired artefact has passed a check it failed. |
| `zodSchema()` / `jsonSchema()` constraining generation at the provider | **ADAPT** | Already stronger at authoring time via the type system; extended by the lint allowlist, which closes raw intrinsic markup — the one case types genuinely cannot see. |
